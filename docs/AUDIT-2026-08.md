## Executive summary

The engineering standard in this repository is genuinely high. The Rust/TS boundary is clean, the phase discipline is real, comments explain *why* rather than *what*, and — unusually — the code is mostly honest about its own gaps (`spout.rs` says it is a stub; `status.rs` labels `missed_pulls_proxy` a proxy). The `verify-phaseN.ts` scripts are real behavioural tests, not source-text greps.

The serious findings are not sloppiness. They are all one failure mode: **a status or liveness signal that fails open.** Four independent subsystems reported "live" or "healthy" on evidence that did not support it:

1. The ON-AIR health lamp measured a JavaScript timer, not painted frames (**S0-1**).
2. Election data defaulted to `sourceStatus: "live"` in five places, including fabricated `Math.random()` vote totals and the sample payload seeded at app startup (**S0-2**).
3. One unrelated panic could poison a mutex and permanently kill Program output, status, and the document stream for the rest of the process (**S0-3**).
4. A source that had never delivered a single payload was never marked stale, so it kept its registered status forever (**S0-2e**).

For a broadcast graphics engine, that class of bug is the one that matters most: the operator's confidence signals were the least trustworthy part of the system. All four are fixed and pinned with tests.

The largest remaining structural risk is **S1-9**: the NDI frame path encodes and decodes a PNG per frame, which caps throughput below the 1080p50 the project treats as its target. That is architectural, not a bug, and the standard answer to it — GPU texture sharing — is the still-stubbed **S2-10**. Everything above S1-9 in the table is fixed, including the Windows-only code that until now had no CI job on any Windows runner (**S1-7**).

## S0-1 — The ON-AIR health lamp measured a timer, not the picture · FIXED

**Where:** `src/views/ProgramView.tsx:43-56` (before fix), `src-tauri/src/status.rs:37-39`

`status.rs` is the ON-AIR authority. It derives `programState` (`Live`/`Stalled`/`NoConsumer`) and `health_pct` purely from the rate of hits on `/program/tick`, and its own doc comment asserted:

> *"This is the only source of truth for 'is something actually pulling /program' — nothing here is fabricated or timer-simulated."*

Those hits came from `ProgramView`, which generated them with `setInterval(tick, 1000 / fps)`. A `setInterval` is exactly a timer simulation. It keeps firing at full rate regardless of whether the page paints anything — an occluded or suspended WebView, a lost GPU process, a Konva/R3F render loop throwing every frame, a frozen composite. In all of those the picture is dead and the lamp reads a steady **Live, 100% health**.

This is the inversion that matters: the one indicator whose entire job is to tell an operator that Program is alive was structurally incapable of detecting the failure it existed to catch. The failure is also silent and confidence-inspiring, which is worse than no indicator at all.

**Fix:** the heartbeat is now driven by `requestAnimationFrame`, which is compositor-driven and stops when the page stops presenting frames. Added a single-flight guard — the old fire-and-forget loop could queue requests faster than the sidecar drained them at 50/60 fps. `status.rs`'s comment now states accurately that it is only as honest as its caller, and what breaks if the heartbeat ever moves back to a timer.

**Honest limits of the fix:** it proves the Program page is alive and presenting. It does not prove the *content* changed (a static lower third is legitimately on air, so this is correct), and it does not prove a downstream consumer received anything. True end-to-end proof needs a returned-frame check from the NDI/OBS side — see `REMEDIATION_PLAN.md` R4.

**UNVERIFIABLE-HERE.** To confirm on Windows: launch the app, point OBS at `http://127.0.0.1:4977/program`, confirm the Output panel reads Live at ~project fps; then suspend the WebView renderer process (Task Manager → *Suspend* on the app's `msedgewebview2.exe` renderer). The lamp must drop to `stalled`/`no_consumer` within ~3s (`STALE_THRESHOLD`, `status.rs:7`). Before this fix it stayed Live.

## S0-2 — Election data failed open to "live" in five independent places · FIXED

This is the most serious finding in the audit. Five separate code paths each defaulted to `"live"`, and they compounded: fabricated election numbers reached the on-air status indicator flagged as a real feed, with no single place an operator could catch it.

**(a) The simulator stamped random numbers as live** — `src/ar-system/dataHub/electionSimulator.ts:11-27`

`mutateElection()` generates vote deltas with `Math.floor(Math.random() * 5000) + 500`, recomputes percentages and ranks, then set `sourceStatus: "live"` on the result. Started from the Data Sources panel (`DataSourcesPanel.tsx:231`), it published invented vote totals every 3 seconds under a live flag.

**(b) The startup sample was marked live** — `src/ar-system/validation/electionSchema.ts:123` (before fix)

`ELECTION_SAMPLE_JSON` — "Candidate Alpha", 1,245,000 votes, 52.3% — carried `sourceStatus: "live"`. `initElectionFeed()` (`election/electionFeed.ts:12-16`) is called unconditionally on mount from `PersistentShell.tsx:65`. **On a cold launch, before any operator action, the election feed was populated with invented vote totals flagged live.**

**(c) The schema defaulted absent attribution to live** — `electionSchema.ts:23`

`sourceStatus: z.enum([...]).optional().default("live")`. Any payload omitting the field — including every payload reconstructed by `parseElectionInput`'s flat-key branch, which never sets it (`electionSchema.ts:88-92`) — was silently promoted to live.

**(d) A broken binding fell back to live** — `src/ar-asset-builder/presets/election.ts:163`

`{ targetPath: "states.alert", source: "election.sourceStatus", fallback: "live" }`. The fallback fires precisely when the binding *cannot resolve* — i.e. when the feed is absent or broken. The breaking-result alert therefore rendered its live state exactly when there was no live data.

**(e) The data hub was born live and could never go stale** — `src/ar-system/dataHub/dataHub.ts:28-37, 150-160`

The constructor registered the election source with `status: "live"` and `lastUpdateAt: null`, so a cold hub reported a live election feed with zero packets ingested. Worse, `tickStaleCheck()` opened with `if (conn.lastUpdateAt && ...)` — a source that had **never** received data has `lastUpdateAt === null`, so it was skipped by the staleness sweep entirely and kept its registered status indefinitely. The staleness check could not fire on the one case that most needed it. `ingest()` then hardcoded `status: "live"` on success, overwriting any attribution the payload carried.

**Fix (all five):**
- `DataPacketStatus` gains `"simulated" | "sample" | "unknown"` and an `isLiveStatus()` predicate, so "not live" is a first-class, checkable state (`dataHub/types.ts`).
- The simulator stamps `"simulated"`; `ELECTION_SAMPLE_JSON` is `"sample"`.
- The schema defaults to `"unknown"`, never `"live"`.
- The preset fallback is `"unknown"`.
- The hub registers `"offline"`, propagates the payload's own declared status through `ingest()`, marks never-updated sources `"offline"` on a stale tick, and ages simulated feeds on the same clock as live ones.
- `electionBehaviour.ts` gains a `source-not-live` event so any non-live data reaching Program is surfaced in the operator's event log, not just `"stale"`.

**Deliberate trade-off:** a *real* feed that omits `sourceStatus` now reads `"unknown"` rather than `"live"`. That is a visible, correctable under-claim; the previous behaviour was an invisible over-claim. For election night, under-claiming is the only defensible direction.

**Pinned by:** `src/ar-system/dataHub/dataHonesty.test.ts` — 9 tests, one per path plus the staleness transitions.

## S0-3 — One panic anywhere permanently kills the entire output plane · FIXED

**Where:** `src-tauri/src/lib.rs` (`program_handler`, `program_tick_handler`, `document_handler`, `document_stream_handler`, `status_handler`), `control_server.rs:230`, `record.rs:90,216,254,263,279`

Every output-plane HTTP handler reached its shared state with `.lock().unwrap()`. In Rust, a thread that panics while holding a `Mutex` **poisons** it, and every subsequent `lock()` returns `Err` forever. With `.unwrap()`, each of those becomes a fresh panic.

The blast radius is the whole output plane at once, because they share two mutexes (`state.doc`, `state.stats`): `/program`, `/program/tick`, `/document`, `/document/stream` and `/status` all die together, permanently, for the remaining life of the process. OBS's Browser Source stops updating, the ON-AIR lamp stops reporting, and the only recovery is restarting the application — mid-show. The triggering panic can be in completely unrelated code.

**Fix:** added `lock_recover()` (`lib.rs:44-63`), which recovers the guard via `PoisonError::into_inner()` and logs once, and applied it at all 11 call sites. The protected data is a `String` envelope and a request-rate counter: the worst case from continuing is one stale envelope or one miscounted hit, which is strictly better than losing Program output. Poisoning is an advisory signal, not a memory-safety hazard — continuing is sound. Test-only `unwrap()`s in `mos.rs` are untouched; panicking in a test is correct.

## S1-4 — Live data ingest re-baked the output once per key · FIXED

**Where:** `src/document/externalConnector.ts:142-161` (before fix), against `src/document/dataSources.ts:161-164`

`dataSources.ts` documents the hazard exactly, on `mergeFeedValues`:

> *"Batch merge — ONE store update (one resolve+push) for a whole incoming payload, instead of one per field. Live REST/WS sports feeds depend on this: 25 sequential setFeedValue calls = 25 full output bakes."*

`mergeExternalValues` — the function on the live REST poll path (`useExternalDataPoller.ts:21`) and the CSV import path (`externalConnector.ts:173`) — called a **per-key setter in a loop**. `mergeFeedValues` was used by exactly one caller, `sportsConnector.ts:61`; the general external connector, the one an operator actually points at a scoreboard API, did the thing the comment warns against.

Each setter is a full Zustand write, and each write re-resolves bindings and re-bakes the output envelope. A 200-key payload cost 200 output bakes, repeating at the operator's poll interval (minimum 2s, `externalConnector.ts:35`).

**Fix:** split routing from writing. `routeExternalValues()` buckets keys by target source with no side effects; a new `mergeSourceValues()` on the store applies every bucket — across feeds, sports, mock/brand/ticker — in a **single** store write. Unknown source ids are dropped rather than creating a phantom source the binding resolver never reads.

**Pinned by:** `externalConnector.test.ts` — asserts a 5-key, 3-source payload produces exactly **1** store notification (was 5).

## S1-5 — Two-column CSV was silently misparsed into wrong bindings · FIXED

**Where:** `src/document/externalConnector.ts:109-139` (before fix)

Found by a test written for the batching fix above — not by reading the code.

`parseCsvToValues` had three branches, and the key/value branch was ordered ahead of the header/row branch with an overlapping guard: `first.length === 2 && lines.every(l => parseCsvLine(l).length <= 2)`. A normal two-column export —

```csv
home,away
2,1
```

— matched it, so **every** line including the header was read as a `key,value` pair, producing `{home: "away", "2": "1"}` instead of `{home: "2", away: "1"}`.

Two columns is the most common shape an operator exports from Excel, and the corruption is silent: bindings resolve to plausible-looking wrong values (`home` = the literal string `"away"`) with no error anywhere. A scorebug would go to air showing the wrong thing while every status indicator read healthy.

**Fix:** reordered and disambiguated. An explicit `key,value` header still wins; **exactly two lines** is now read as header + data row at any width; three-or-more rows no wider than two columns remains a headerless key/value list. **Pinned by** 4 CSV tests covering all three branches plus quoted-field escaping.

## S1-6 — There was no unit test framework · FIXED (framework), OPEN (coverage)

**Before:** no vitest, no jest, no test runner of any kind. All 45,371 lines of TypeScript were covered by 12 hand-rolled `scripts/verify-phaseN.ts` files.

Credit where due: those scripts are **real behavioural tests** with a working assertion harness, not the source-text greps this pattern usually degenerates into (only `verify-sports-ar-models.ts` reads source files). The problem is structural, not qualitative:

- **Phase-scoped and additive.** Each pins the phase that created it. Nothing re-tests earlier phases against later changes, so cross-phase regressions have no net.
- **Unreachable units.** The data-source, data-hub, binding-resolution and connector paths — the code that decides what actually reaches Program — had no coverage at all. Both S0-2 and S1-5 lived in exactly that gap for multiple phases.
- **No watch mode, no coverage, no isolation**, so tests are not part of the edit loop.

**Fix:** Vitest 3.2.7 + happy-dom, `vitest.config.ts` deliberately separate from `vite.config.ts` (the app config carries Tauri dev-server, HMR and three/`realism-effects` shim plumbing a headless run does not need; only the `@/` alias must match, and it is asserted). Scripts: `test`, `test:watch`, `test:coverage`. 46 tests, each pinning a defect fixed or a contract established in this pass.

The `verify-phaseN.ts` scripts are **kept and still run in CI** — they are the phase-level acceptance layer and duplicate none of this.

**Still OPEN:** 46 tests against 45k lines is a seed, not coverage. Priorities in `REMEDIATION_PLAN.md` R5: binding resolution, `timelineEngine`, `playout`, `automation` conditions, `persistence` round-trip.

## S1-7 — The Windows-only output path had no Windows CI · FIXED

**Where:** `.github/workflows/ci.yml`

Both CI jobs run `ubuntu-latest`. But the product's most fragile, least portable, most safety-critical code is Windows-only and compiled out everywhere else:

- `capture.rs:18` — `#[cfg(windows)]` WebView2 `CapturePreview`, COM/`IStream`/`HGLOBAL` handling
- `ndi.rs` — `libloading` dynamic NDI SDK binding, hand-rolled FFI
- `spout.rs` — Windows/macOS GPU texture sharing
- `Cargo.toml` — `webview2-com` and `windows` crates pinned with `=` to match Tauri's vendored versions exactly

Nothing on Linux compiles, let alone exercises, any of it. A change that breaks the NDI FFI surface or drifts the pinned `webview2-com` version passes CI green and fails on the operator's machine. Hand-rolled FFI plus exact-version pins is precisely the code that most needs a compile gate.

The design note in `ci.yml:4-6` explains why *bundle* builds are excluded, which is reasonable. It does not address `cargo check` on Windows, which is cheap.

**Fix:** added a `verify-rust-windows` job (`windows-latest`) running `cargo check --tests` and `cargo test --lib`. No NDI SDK is installed, deliberately — `ndi.rs` dynamic-loads at runtime rather than linking at build time, so a machine without the SDK still compiles and honestly reports unavailable. That design is what makes this job cheap, and this job is what stops that design breaking silently. Also wired `bun run test` into the frontend job, since Vitest now exists (S1-6).

**Not verified here:** GitHub Actions cannot be executed in this container. The workflow YAML parses and the job graph is `verify-frontend`, `verify-rust`, `verify-rust-windows`; the Windows job's first real run is its own proof.

## S1-8 — `take()` was a bare alias of `cut()`, eight phases on · FIXED

**Where:** `src/document/programState.ts`

```ts
take: () => { get().cut(); },
```

with the comment: *"Phase 2: an instant alias of cut(), kept as its own named action/button so Phase 3 can give it a real animated transition."* The repository is at **Phase 10.2** — Phase 3 shipped seven phases ago, and a Take that cannot mix is a table-stakes gap for every product in this class.

**Fix:** the seam is filled in. `cut()` is untouched and still a hard instant switch; `take(override?)` now runs a real timed transition.

- **`src/document/sceneTransition.ts`** (new) — the whole visual contract as pure functions, so renderers and tests agree by construction. Two types: `dissolve` (true A/B mix, crossing at 50/50) and `dipToClear` (sequenced — the outgoing scene is fully gone before the incoming one comes up). Named *dip to clear*, not *fade to black*: this engine outputs an alpha overlay, so there is no black to dip through, and calling it "fade" would invite exactly the wrong expectation.
- **State model copied from `cameraMoves.ts`**, deliberately: transient (never persisted — a half-finished dissolve restored across a restart is meaningless), keyed on a wall-clock `startedAt` so the Program window, the Preview window and the sidecar-served renderer OBS reads each reconstruct the same mid-mix frame with no sync protocol, and **end state committed up front** — `programSceneId` is the incoming scene from the instant of the take, so a consumer that renders zero in-between frames still lands on the correct final frame. That last property is what makes a stale record harmless: past `durationMs` the math returns the settled end state, so clearing is housekeeping, never correctness.
- **`TransitionCompositor`** renders the committed incoming scene and paints the outgoing one back on top at falling opacity, unmounting it (and releasing its WebGL contexts) the moment the mix settles. Wired into `ProgramView` (which is also what OBS loads through the sidecar) and the multiviewer's PGM tile. The PVW tile does not mix — it shows the armed scene, which a take does not animate.
- **Determinism under pressure:** a take landing mid-transition replaces the in-flight record outright rather than stacking a three-way blend; `cut()` snaps any mix (a CUT mid-dissolve is an operator saying *now*); `setProgramDirect`/`hydrateProgramState` clear it too.
- **Control surface:** the `take` control command accepts optional `type`/`durationMs`, so a panel can bind separate MIX and CUT buttons to one command. Unknown values fall through to the operator's default. Additive to the wire protocol — existing senders are unaffected.

**Two non-obvious things this needed, both caught during implementation:**

1. `cut()` prunes `layerPlayback` to the incoming scene's layers, and a timelined gfx2d layer with no playback entry renders as off-air. Without intervention every timelined layer in the outgoing scene would vanish on frame one — graphics would *pop off* and only the untimelined backplate would dissolve, which reads worse than a plain cut. The transition record now carries a `fromLayerPlayback` snapshot taken before the prune, keeping `cut()`'s semantics untouched and the record self-describing.
2. `take()` commits the scene change (via `cut()`) and installs the record in a *second* store write. The envelope-push subscription watched only the scene ids, so it fired on the first write — when `transition` was still null — and early-returned on the second. The dissolve never reached the envelope and Program/OBS cut instead of mixing. The subscription now watches `transition` as well, while still only persisting on a genuine scene change.

**Pinned by:** `sceneTransition.test.ts` (12) — mix math, dissolve summing to 1 throughout, `dipToClear` never showing both scenes at once, settled end state, unknown-ease fallback, staleness. `programState.test.ts` (12) — end-state-first commit, default/override/clamping, explicit cut, no-op guards, mid-transition replacement, the playback snapshot, and `cut()` snapping a mix.

**UNVERIFIABLE-HERE.** The visual needs a running app: arm a scene, press Take, and confirm Program and an attached OBS Browser Source show the same dissolve at the same point in time. See R0.

## S1-9 — The NDI frame path encodes and decodes a PNG per frame · OPEN · UNVERIFIABLE-HERE

**Where:** `src-tauri/src/capture.rs:18-100`, `Cargo.toml:profile.dev.package.*`

Program frames reach NDI as: WebView2 `CapturePreview` → **PNG encode** → `IStream`/`HGLOBAL` copy → **PNG decode** → BGRA convert → NDI send. PNG is a lossless, entropy-coded still-image format; this is a full compress/decompress round trip per video frame, on the CPU.

The codebase already documents the severity: `Cargo.toml` needs `opt-level = 3` overrides on `image`/`png`/`miniz_oxide`/`fdeflate`/`crc32fast` in **dev** builds because decoding one 1080p frame took ~2s unoptimised versus ~30ms optimised, throttling capture to ~0.5 fps. Even at the optimised ~30ms decode, decode alone caps throughput near 33 fps before encode, copy, convert or send — below 1080p50, which `docs/BENCHMARK_1080P50.md` treats as the target. `in_flight` correctly serialises captures, so the pipeline self-throttles rather than queueing; the ceiling is real, not a backlog artifact.

The choice is defensible for the constraint it was made under (PNG preserves the alpha the transparent overlay needs, and needs no GPU capture path). It is not a broadcast-rate video pipeline, and the product class solves this with GPU texture sharing or DeckLink/2110 (see `GAP_ANALYSIS.md`).

**UNVERIFIABLE-HERE** — no Windows, no WebView2, no NDI network. To measure: run `scripts/verify-phase8.ts`'s benchmark path on Windows with NDI Tools' Studio Monitor attached and record achieved fps against the project's 50.

## S2-12 — Sidecar bind failure ends in a silent dead sidecar · OPEN

## S3-15 — Stale documentation · OPEN

- `README.md` is still largely the **Tauri + React + Typescript template README** for a 45k-line broadcast product. It documents the Windows dev-restart workflow well, and nothing else — no description of what the product is, no architecture, no run/test instructions.
- `docs/ar-system-audit.md` is dated 2026-07-09 (~Phase 5) and is now materially wrong in both directions: it lists the OBS dev redirect as **BROKEN** on port 1420 (it is 1423 today, `lib.rs:271`), and reports "no Data Hub, no property registry, no behaviour engine" — all three now exist (`src/ar-system/{dataHub,propertyRegistry,behaviour}`). ## What was audited and found sound

Stated explicitly, because an audit that lists only problems misrepresents the codebase:

- **Undo/redo isolation** — `programState.ts:6-13`: PGM/PVW is a sibling of `project`, excluded from zundo's `partialize` *by construction* rather than by a guard someone must remember. Correct design, correctly explained.
- **`status.rs` rate maths** — the rolling-window rate, `STALE_THRESHOLD` and stalled-ratio logic are sound and genuinely well tested (5 unit tests covering the real transitions). The defect in S0-1 was entirely in its caller.
- **NDI availability honesty** — `ndi.rs:5-13` distinguishes `available: false` with a *specific* reason from a generic failure, and reports `connections` as `None` before `start()` rather than a fake `0`. Dynamic loading via `libloading` (the NDI SDK's own recommended pattern) means the app builds and runs honestly on machines with no SDK.
- **`useSyncExternalStore` discipline** — `dataHub.ts:19-22`, `electionBehaviour.ts:19-21` and `dataSources.ts:275-282` each cache snapshot identity, with comments recording the live React 19 infinite-remount loops that motivated them. This is hard-won knowledge, correctly preserved.
- **MOS implementation** — `mos.rs` (1,180 lines) uses a streaming `quick-xml` reader with a documented rationale over whole-DOM parsing, and carries 12 unit tests including `\x00` terminator handling and parser round-trips of its own builders.
- **The `verify-phaseN.ts` suites** — real assertions on real behaviour.
- **Renderer/editor split** — one pure `renderElement()` builder feeding both the interactive Konva editor and the non-interactive `DocumentRenderer`, so Program cannot drift from the editor by construction.
